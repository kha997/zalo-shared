# Private connector reconciliation

This is an admin-only recovery workflow for the private application. It enables neither real Zalo login nor production deployment. Disabled mode remains disconnected. All development evidence uses synthetic identities, bytes and SDK-shaped calls.

## Before an operation

Open “Đối soát Zalo” with a current active administrator account. Review mode, connection, owner phase, gap version and held/conflict/unknown counts separately. Socket connection alone does not establish complete history. Agents and supervisors can see availability summaries but cannot inspect or mutate recovery evidence. Mutation requests require the current session, exact Origin, CSRF token and a fresh admin check inside the transaction.

Record a nonsecret evidence reference to an independently retained investigation. Do not paste cookies, signed URLs, credentials or customer text into that reference. The software records your attestation and exact IDs; it cannot verify a phone screen, firewall rule or external investigation. A 409 means the snapshot changed or work is busy: refresh, review the new evidence and explicitly decide again. Never blindly repeat a mutation.

## Unknown sends

Do not send the message again. Select the original unknown message/part and a nonconflicting held outbound event from the same conversation. Confirm only an exact provider ID independently observed for that part. The service preserves the original staff author and already accepted parts; it finalizes the message only when every part is confirmed or skipped. It performs no SDK send. There is no reset-to-pending, retry, bulk confirmation or arbitrary native-classification command. Missing or ambiguous evidence stays unknown.

## Conflicting receipts

Compare the canonical normalized receipt with every retained variant. Canonical content and all retained variants remain immutable evidence; the supported decision retains the canonical record after explicit external review. A new variant reopens the conflict. At most eight differing variants are retained; overflow, legacy missing evidence and exhausted versions are blocked from this workflow. Escalate for investigation rather than editing database evidence or pretending the record is complete.

## History gaps and ownership

Acknowledge a history gap only after an external review and after all held events, unresolved conflicts and unknown/processing jobs are resolved. The acknowledgement compares the exact gap version and owner identity/epoch; a new fault must win or invalidate a stale acknowledgement. It keeps the provider disconnected and does not certify complete history. The injected runtime conservatively keeps its local gap gate closed; the current library requires a separately fenced/admitted runtime to resume after a gap. Private activation and improved supervised resume remain later gates.

For takeover follow [CONNECTOR-FENCING.md](CONNECTOR-FENCING.md). Stop and independently verify isolation of the old process and its external provider egress before attesting. A released database lock, elapsed heartbeat or SDK stop does not prove external fencing. Never acknowledge if the old runtime cannot be located. Fencing does not clear unknown messages or the independent history-gap gate.

## Recovery and evidence

Backups contain normalized customer content, provider IDs, variants, attribution and administrator evidence references. Restrict access accordingly. Restore verifies original counts/content hashes before quarantining sessions, jobs, provider and ownership; gap versions advance without wrap. Keep all provider network access disabled until an explicit reviewed recovery. Locator encryption keys are a separate recovery requirement once inbound jobs are integrated.

The current database audit is protected against the application runtime role, not against a database owner; external immutable audit storage remains a production gate. Production retention, storage budgets and deletion policy need Owner decisions; no evidence deletion or automatic purge is added here. Real-account phone coexistence, platform terms/account-ban risk, inbound CDN compatibility, notification delivery and low-volume soak remain separate acceptance gates. Never use HANU production or real customers for the pilot.
