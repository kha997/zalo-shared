# Reproducible acceptance protocol — not yet executed against Zalo

Use only a separately owned, legitimately registered test account, one consenting test peer account, synthetic contacts/messages and a dedicated phone. Never HANU production. Account owner controls QR reauthentication privately; do not paste cookies, QR images or tokens into evidence. No public API endpoints. Connect workstations over LAN/private VPN with TLS; expose backend only to Chatwoot/private gateway. Pin every container by digest and source SHA; record hardware, versions, dependency lock hashes, configuration *names* and sanitized timestamps. Assign four distinct application logins A–D; Zalo remains one shared backend identity. A terminal callback is not a workstation test.

Record each step in CSV: run_id,test_id,source_sha,started_utc,client,synthetic_message_id,expected,observed,status,evidence_path. Redact phone/account identifiers and tokens before exporting evidence. FAIL means a witnessed mismatch or a source-proven missing required control; UNPROVEN includes blocked, not run, and documentation-only claims. Never upgrade a mock PASS into integration PASS.

| ID | Reproduction | Gate / evidence |
|---|---|---|
| C4 | Four independent browser profiles on four workstations, A–D log in simultaneously. Peer sends 100 uniquely tagged inbound texts; barrier-start four agents sending 25 unique texts each. Record UI and DB counts. | Exactly 100 inbound +100 outbound unique records; each authorized workstation sees every applicable item once; sender identity retained; no logged-out staff session; report latency p50/p95. Proposed usability gate p95 <5s on measured network. |
| COLLISION | A/B open same conversation and send different replies concurrently, then retry same client request key after timeout. | Both intentional replies preserved/attributed, one send per retry key; assignment conflict explicit; no silent overwrite. Assignment is not an exactly-once lock. |
| PHONE | While C4 runs, phone remains active, reads/sends 20 unique texts and 5 synthetic images; peer replies; rotate phone Wi-Fi/cellular and lock/unlock. | No forced phone logout; phone-originated messages appear once in inbox with Zalo-self/phone attribution (not a fabricated agent); all test peer receives intended items. Record phone/app/OS version. |
| MEDIA | Both directions: tiny PNG, JPEG, GIF, PDF, voice/audio, short video; unsupported type, configured oversized file, 3 attachments with failure on second. Hash original/downloaded bytes where protocol preserves originals. | Supported types deliver/open; UI accurately reports unsupported/rejected/partial outcomes; attachments 2/3 survive retry, no repeat of attachment1. Preview transformation may change hashes; distinguish originals. |
| INVALIDATE | Owner revokes web session on phone; separately expire a synthetic adapter token, and open another Zalo Web session deliberately on test account only. | Queue stops sends; health changes to reauthentication-needed; four UIs alerted within 60s; no retry storm or credential leakage; owner reauth restores service. Actual provider behavior recorded separately from injected failure. |
| RECONNECT | Drop adapter network 30s/5min; restart worker; restart Chatwoot; stop worker during retry backoff; kill process after upstream send but before local commit. | One active listener, no resurrection after stop, persisted queued work recovers, confirmed messages not resent; ambiguous delivery held for reconciliation. Measure missing/recovered events; do not assume full upstream history available. |
| DEDUP | Replay each inbound/provider ID and Chatwoot webhook 10 times concurrently and after process/DB restart; reuse same ID in another thread/account; reorder old/live events. | One logical message per scoped ID; unique DB keys effective; unrelated scoped IDs survive; intentional identical text allowed. |
| AUTH | Anonymous, expired, wrong-user, revoked-user requests; forged/tampered/stale/replayed webhook; agent attempts QR/session/admin APIs, foreign inbox/room IDs, attachments without auth. | Requests rejected with 401/403 where applicable; no body/media/socket disclosure; replay cannot enqueue another send; authenticated room membership derives server-side. |
| AUDIT | A–D each send/edit/delete/assign; admin revokes C; phone sends; inspect exported audit and request logs. | Actor, operation, provider/local IDs, UTC timestamp, result retained; no cookie/token/content overlogging; phone sender accurately unknown/shared identity. Audit must include security/admin events, not just message transcripts. |
| DURABILITY | Queue 100 messages, SIGKILL worker/DB at selected boundaries, reboot, restore fresh DB and media from encrypted backup, then recover adapter secrets privately. | Committed records/media survive; restore counts and hashes match; outbox/inbox/queue/mappings restored consistently. Proposed RPO <=24h with daily backups; proposed RTO <=2h demonstrated, not promised. No claim of zero loss before local receipt. |
| SOAK | 7–14 days low-volume synthetic interaction, including idle overnight, daily phone check, reconnect and restore drill. | No unexplained gaps/duplicates or forced logouts; no warnings/restrictions; collect uptime and operator effort. Short-term success does not establish ban safety. |

Stop on account warning/restriction, unauthorized data disclosure, repeated listener eviction, unexplained missing/duplicate sends, or credentials in logs. Disable sends first, preserve sanitized evidence, revoke the test session, and restore the test account to official phone use. Never evade provider detection or automate new accounts.

## Phases and decision gates

1. Offline remediation (estimated 3–7 engineering days): reproducible locked build, SBOM/advisory review, webhook authentication, strict schema/size limits, private network configuration, encrypted session storage, one fenced adapter, persistent per-message/per-attachment dedup/outbox, failed/ambiguous send handling, safe logs and shutdown tests. Re-run the observed failure cases. No upstream/production repository edits authorized by this research are necessary: maintain experimental fork/patches only in isolated new workspace if later commissioned.
2. Private synthetic integration (2–3 days): run Chatwoot/PostgreSQL/Redis/bridge in isolated network; no Zalo credentials yet. Execute C4/AUTH/DEDUP/AUDIT/DURABILITY with simulated provider; verify ports from a separate host; publish no endpoint. Choose exact Chatwoot stable version/edition and verify its security features/license rather than using moving develop/latest tags.
3. Separate-account pilot (7–14 days elapsed, 2–4 operator days): legitimate owner phone + test peer + four staff; execute every live step above. Requires an available dedicated phone/account and explicit owner participation. No production account or customer history.
4. Decision review: compare actual results, residual platform/ban risk, licensing and support burden. Any later production proposal requires separate authorization and preferably provider approval or an official Zalo OA integration feasibility study. No production approval follows from this document.
