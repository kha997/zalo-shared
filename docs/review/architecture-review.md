# Independent architecture review

Review date: 2026-10-27. Scope: proposed original Node 24/TypeScript, Fastify REST/SSE, React, PostgreSQL shared inbox with mock provider. This is a specification review, not a code audit or evidence of working delivery. Sources: `/workspace/zalo-study/REPORT.md` and `bridge-findings.md`, including their stated limitations. No real account, authentication, production, or upstream writes are authorized.

## Decision and tradeoff

Proceed with an original **synthetic pilot**, conditional on the invariants below. Research selected hardened bridge + Chatwoot as the best existing pilot foundation; this proposal changes that choice and must explain why. Chatwoot supplies established inbox UX, users and workflow, but adds integration/webhook delivery boundaries and edition-specific audit/permission constraints. Its inspected develop snapshot is not a validated stable deployment. Original development makes transactional application state, role controls and audit easier to reason about together, but transfers responsibility for authentication, authorization, accessibility, media security, pagination, retention, upgrades and operations to this repository. A working mock demo does not establish lower overall engineering cost or superior production security.

Keep the transport replaceable. Do not copy candidate application code with ambiguous licensing. Preserve notices for any deliberately reused licensed code. Keep live adapter disabled by construction with no SDK import, credentials, QR endpoint or login path in the default executable. Separate enablement and deployment authorization from ordinary application configuration.

## Required invariants

1. **Account isolation:** every conversation, message, attachment, provider ID, request key, queue job and SSE event belongs to an account. Scoped uniqueness includes account and message direction/type where the provider ID namespace requires it. Even with one configured account, a guessed foreign account/resource ID must fail server-side. Never trust an account ID supplied by the browser as authorization.
2. **Atomic acceptance:** a send response means a transaction durably committed the outgoing message, outbox job and attributable audit record. An inbound acknowledgement follows durable inbox commit. Repeated request key + same canonical payload returns the original outcome; same key + different payload returns conflict. Identical text with different keys remains legitimate.
3. **Honest delivery:** persist separate queued, dispatching, confirmed, failed and unknown outcomes; support per-part progress if media is included. A timeout, process kill or connection loss after possible remote acceptance becomes **unknown**, not success or retryable failure. Never automatically resend unknown deliveries. Provider idempotency or trustworthy reconciliation is required to remove uncertainty. Exactly-once local insertion is achievable; exactly-once remote delivery is not established by queue uniqueness.
4. **Exclusive transport:** one account has one active listener/dispatcher. PostgreSQL lease acquisition uses database time, monotonic fencing token and guarded renew/commit. A worker loses permission immediately on renewal failure, closes its provider connection and stops dequeueing. **A database fencing token cannot stop a paused obsolete process from sending to a provider that does not validate tokens.** Restrict live operation to one process with confirmed termination before takeover, or introduce an exclusive egress owner that enforces tokens. A TTL alone does not prove safe live failover.
5. **Assignments and concurrency:** claiming/reassigning uses an atomic conditional update or version precondition. Define whether only assignee may send, and which role may override; enforce it within the send transaction. Display authoritative conflicts, avoid silent last-write-wins, and ensure two staff cannot unknowingly acquire the same conversation. Simultaneous intentional messages require distinct request keys; serialization must not merge them.
6. **Authority stays current:** each API and SSE connection checks an active user, current role and account membership. Revocation terminates or prevents further events on existing streams. Owner controls staff/roles and adapter lifecycle; supervisor may assign/reassign and inspect audit; agent performs permitted inbox actions. Explicitly decide visibility of unassigned/other-agent conversations. Never grant transport/session secrets to ordinary staff.
7. **Session safety:** opaque cryptographically random server-side sessions, hashed session tokens at rest, password hashes with a supported password KDF, session rotation on login and privilege changes, idle/absolute expiry, logout revocation and bounded login attempts. Cookies are HttpOnly, Secure under TLS, SameSite and narrowly scoped; local HTTP exception is explicit and loopback-only. SameSite alone is insufficient CSRF protection: verify allowed Origin and require a per-session CSRF token for mutations. No state mutation via GET. Disallow wildcard credentialed CORS and query-string SSE tokens. Never rely on localStorage bearer credentials as the default.
8. **Protected audit:** transactional actor/action/resource/outcome/request identifiers and timestamp for sends, assignments, user/role/session lifecycle and adapter administration. Application DB role cannot update/delete audit rows; migrations use a distinct owner. Store no password, cookie, QR, message body or secret in audit/error logs. Local append-only permissions do not protect against DB owner compromise; an external protected sink is needed for stronger immutability claims. Native phone sends must be attributed as native/shared identity, not guessed staff.
9. **Durable replay:** SSE is a notification mechanism; PostgreSQL is the source of truth. Reconnect uses an authorized persisted cursor or refetch. Cursor gaps, retention expiry and slow consumers trigger a bounded resync. Event IDs must not leak cross-account payloads. Marking an event delivered to a browser is not message delivery to Zalo.
10. **Recoverable storage:** backup and restore include database, media, configuration and recoverable encryption keys. Document measured RPO/RTO. Restoring an older outbox can replay previously sent messages: restore starts with dispatch disabled, reconciles jobs and quarantines uncertain sends before enabling. A successful SQL dump alone is not a restore drill.

## Concrete acceptance gates

| Gate | Evidence required |
| --- | --- |
| Four staff | Four independent browser contexts/users concurrently authenticate, receive incoming events, observe assignment conflict, send and reconnect; screenshots plus machine assertions. Browser contexts prove application concurrency, not four physical workstations or phone coexistence. |
| Scale | Repeat stated workload at 10/25/50 authenticated users; report hardware, dataset, duration, concurrency, messages/sec, p50/p95 latency, error rate, DB/CPU/memory and queue age. No hard-coded seat cap; 50 users is a measured point, not unlimited capacity. |
| Authorization | Agent cannot create users/change roles/access adapter secrets; disabled user and downgraded role lose API/SSE access. IDOR checks cover reads, sends, assignment, SSE replay, audit and media, not only list endpoints. |
| Browser safety | Missing/wrong CSRF token and foreign Origin fail; cookie flags, fixation, expiry/logout, brute-force limits, CORS, persisted message XSS and error redaction are tested. |
| Concurrency | Parallel claim and stale-version mutation have one authoritative winner; duplicate send keys create one message/job; changed payload with reused key conflicts. |
| Delivery failures | Faults before dispatch, after simulated provider acceptance/before DB commit, during lease loss, and attachment N failure. Unknown outcomes stay visible without automatic resend. Mock must record provider acceptance separately from app state to expose crash windows. |
| Persistence | Kill/restart worker and DB with accepted incoming/outgoing work. Repeat inbound provider IDs concurrently. Committed events survive and unread counters remain consistent. |
| Restore | Restore into fresh database/storage, verify counts, media hashes, role restrictions, audit and cursor replay; prove dispatch starts disabled and sent jobs are not silently replayed. Record elapsed restore time and lost-data boundary. |
| Safe defaults | Default install cannot contact Zalo or produce QR; loopback binding and synthetic data only. No secret/config fallback suitable for accidental exposure. |

## Remaining specification choices

Before declaring the pilot complete, record exact role matrix and agent visibility, supported message types (text-only is acceptable if explicit), send conflict behavior after reassignment, unknown-delivery resolution authority, retention and backup targets, performance thresholds, and native-phone attribution. If attachments are deferred, reject them explicitly in the API rather than silently dropping them. Define input/body limits, pagination and SSE backpressure even for text-only scope.

Live phone coexistence, full history/gap recovery, platform terms/account restriction risk, real send/receipt semantics, provider ID stability and attachment behavior remain unproven and cannot be inferred from this pilot. Production acceptance requires separately authorized real-provider evidence and operational review.
