## Facade compatibility and secret boundary

- `dist/zalo.js:45-72` implements `new Zalo(options).login(credentials)` returning API. There is **no upstream createApi export**; that is a host facade requirement. Credentials must contain imei/cookie/userAgent (`40-43`). Cookie domain normalization mutates supplied entries (`14-19`), so validate and clone vault data before handing it over.
- Defaults are **selfListen:false, checkUpdate:true, logging:true, polyfill:global.fetch** (`dist/context.js:13-24`). Options are assigned before login (`dist/zalo.js:45-48`), so the transport's explicit false/true/false settings are supported. `loginCookie` invokes checkUpdate **before parameter validation** (`50-52`); `dist/update.js:4-16` fetches npm registry unless disabled. Logging false alone does not disable that request. CJS has the same defaults/guard (`dist/cjs/context.cjs:15-25`, `dist/cjs/update.cjs:8-19`, `dist/cjs/zalo.cjs:48-55`). Actual login still performs provider HTTP through login/getServerInfo; it cannot be tested by importing and calling login offline.
- **Secret-bearing exception confirmed in the artifact:** `dist/utils.js:625` and `dist/cjs/utils.cjs:629` throw `Invalid context ` plus JSON.stringify(ctx,null,2). That can include credential/context fields and does not consult logging. Sanitize caught errors at the facade boundary; never expose raw Error/message/cause/context to ordinary logs or callers. Generic authentication exceptions are not reliable invalid-session classification (`dist/zalo.js:59-70`).
- QR GotLoginInfo callback exposes cookie/imei/userAgent before final cookie login and is not awaited (`dist/zalo.js:87-104`). Durable encrypted handoff and explicit bootstrap cancellation remain host responsibilities.
- `dist/apis/getCookie.js:2-7` returns the current CookieJar, and `getOwnId.js:2-3` returns ctx.uid. Persist current jar through controlled serialization; keep raw API/cookies/context private.

## Actual message contracts

Outbound declarations say `{message:{msgId:number}|null, attachment:{msgId:number}[]}` (`dist/apis/sendMessage.d.ts:2-9`). Compiled implementation initializes exactly these keys and assigns response data without converting IDs (`dist/apis/sendMessage.js:410-450`; CJS `422-462`). Existing transport extraction of `result.message.msgId` is appropriate for text. Safe integer numeric IDs can be converted to strings; unsafe numbers cannot be recovered. A returned provider ID establishes acceptance, not delivery or seen status.

Inbound constructors are actual runtime classes (`dist/models/Message.js:2-28`; CJS `models/Message.cjs:5-31`): direct threadId uses raw sender sentinel "0" to select idTo versus uidFrom; group threadId is idTo; isSelf is based on raw sentinel, then sender/recipient sentinels are replaced with account UID. Declarations specify msgId/cliMsgId/uidFrom/idTo/ts as strings (`dist/models/Message.d.ts:15-25`). Existing string-ID validation is supported, but the constructor does not enforce runtime field types; malformed frames still require validation. No equality-of-UID shortcut should replace sentinel semantics.

Text client IDs come from Date.now (`dist/apis/sendMessage.js:185,201`); attachment/upload IDs are generated internally (`253-262`, `dist/apis/uploadAttachment.js:48,84,103,122`). MessageContent has no caller-supplied stable clientId and response exposes only msgId (`sendMessage.d.ts:2-9,68-100`). Incoming cliMsgId alone does not make durable outbox retry idempotent. Current transport drops that field; matching identical text/time is not safe correlation.

## Media and partial effects

`dist/apis/uploadAttachment.js:49-61` accepts file paths or Buffer objects, dispatches by extension and rejects missing files/names/restricted extensions. It is not a MIME/content or private-path boundary. For Buffers it trusts supplied metadata (`77-85,93-123`); chunk counts derive from metadata, while bytes come from actual Buffer slices (`131-139`). Host must independently enforce totalSize===data.length, bounded size/count, verified MIME/extension and bounded image dimensions. Avoid user-supplied paths and use verified immutable private bytes. Path image metadata uses the caller getter (`dist/utils.js:300-334`); JPEG/PNG Buffer metadata bypasses it. This does not validate GIF/video support for the application.

Combined sends can send text before uploading/finalizing attachments (`dist/apis/sendMessage.js:430-443`); component requests use Promise.all (`82-96`). Rejection can therefore hide successful components. Keep text-only first integration, or durable separate per-component attempts and unknown outcomes without automatic resend. Calling one attachment with empty msg is structurally supported but still contains upload/finalize uncertainty.

Generic file/video upload awaits a WebSocket callback (`dist/apis/uploadAttachment.js:160-170`), resolved from control frames (`dist/apis/listen.js:213-226`). Callback map expiry only deletes the map entry after five minutes (`dist/context.js:1-11`); it **does not reject/resolve the awaiting promise**. Listener loss or missing callback can leave uploads pending indefinitely. All upload requests are joined with Promise.all (`uploadAttachment.js:194`); a host timeout cannot establish that upstream work was cancelled.

## Listener and durability blockers

`dist/apis/listen.js:98-144` starts synchronously, opens a credential-bearing WebSocket, emits connected on open, emits disconnected on close, and emits closed when retry is disabled. retryOnClose:false is supported. Close reasons 3000/3003 mean duplicate/kick (`10-16`), not proven cookie-expiration diagnostics. Error events carry unsanitized unknown errors.

**Shared-listener restart race remains:** stop closes and immediately resets (`363-367`), while old socket onclose unconditionally resets this.ws and emits closure (`123-138`); reset clears the current socket/cipher/timer (`413-418`). A late close after restart can erase the newer socket or be received by newer wrapper handlers. CJS preserves the same flow (`dist/cjs/apis/listen.cjs:136-151` and corresponding stop/reset methods). The current `adapters/zalo/transport.ts` reattaches the same API/listener after interruption; wrapper event-generation checks cannot determine which socket emitted a shared event. Require fresh API/listener generations or verified confirmed-close serialization before real integration.

`dist/apis/listen.js:186-190,205-209` calls callbacks and emits messages without awaiting durable host persistence or deduplicating. selfListen must be enabled for self messages. Existing onInbound synchronous callback is not durable ingestion, and asynchronous rejection is not handled by the transport's synchronous try/catch. Bound and observe ingestion, deduplicate transactionally by account/thread/provider ID, retain actor attribution and stop/backpressure on persistence failure. No app-level ack/replay guarantee was established.

Old messages are separate emissions (`294-300`), requested separately (`390-397`); delivered/seen are separate (`326-346`). No verified no-loss recovery, exactly-once delivery, history continuity, cross-process fencing or receipt reconciliation follows from these APIs.

## Scope of conclusion

The published artifact supports the prior text/envelope/options contracts, and confirms the invalid-context leak, media uncertainty and delayed-close hazard. It is eligible for further **offline** facade development with those boundaries. This report is not full security certification, source-to-binary equivalence, transitive advisory clearance, runtime import compatibility, or authorization for real-account/provider/production use. Installation/lockfile audit and facade-specific offline tests remain separate evidence; separate-account live validation remains outside this review.
