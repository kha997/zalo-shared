## Safe media boundary

`src/apis/sendMessage.ts:179` accepts AttachmentSource(s), whose pinned definition was retrieved in follow-up: `src/models/Attachment.ts:1-11` is string or `{data:Buffer, filename:string, metadata:{totalSize:number,width?:number,height?:number}}` (filename is typed as a string containing a dot). `handleAttachment` at 399-418 splits GIFs then calls `api.uploadAttachment`; the upload implementation was retrieved and reviewed in follow-up (see below). File extensions choose image/file pathways. GIF code at 530-542 reads metadata and file bytes, creates a thumbnail and uploads. README:35-60 and `context.ts:151-174` require caller-provided imageMetadataGetter for path-based image/GIF use.

A minimal future host interface should accept a server-owned immutable attachment reference plus validated name/MIME/size and verified bytes, not a user-supplied filesystem path or remote URL. Resolve references inside private storage, enforce existing app size/count/type limits and content checks, then translate into the verified Buffer attachment contract with host-derived metadata. Metadata must be derived server-side from verified bounded bytes; image parsers need their own dependency and resource review. No broad URL fetching is justified by sendMessage's use of SDK-generated upload URLs.

Important partial-delivery behavior: `sendMessage.ts:651-663` can send text **before** uploading/sending attachments; `send():216-236` uses Promise.all for component requests. A rejected aggregate can conceal successful components. A single combined success/failure flag cannot safely retry this operation. Require durable per-text/per-attachment execution records and provider IDs; interrupted/uncertain components remain unknown, with no automatic resend. Safest first integration remains text-only; candidate does not expose media sends.

## Durable inbound constraints

Listener dispatch loops call onMessageCallback then EventEmitter emit without awaiting host persistence or deduplicating provider IDs. Existing local synthetic evidence demonstrates duplicate emission. Current candidate onInbound is synchronous, catches synchronous failures and does not await promises; an async DB callback can reject without being observed, lose an event on process exit or create unbounded concurrent writes. Therefore simply passing an async INSERT callback is **not** a durable ingestion integration.

Minimum boundary: an explicit bounded ingestion service with observed completion/failures, account identity plus thread type/thread ID/provider ID deduplication, transactional persistence and checkpointing, duplicate/self-origin reconciliation, and stop/backpressure on persistence failure. When an emitted provider event cannot be durably retained there is no application-level acknowledgment/replay guarantee in the inspected live event path. History retrieval is a separate API and unverified recovery mechanism. Distinguish phone/self messages from app-origin outbound echoes; preserve actor attribution for the latter instead of inventing a staff actor from isSelf. Model thread mapping is now established by pinned source; deterministic client-message-ID correlation is still unavailable through the public send method.

Lifecycle caveat: upstream WebSocket onclose unconditionally calls reset(), and stop resets without waiting for the old socket close. After an error-driven stop/restart, a late old-socket callback could reset the SDK's newer socket or emit closed into the newer wrapper generation. Wrapper callback tokens cannot identify which underlying socket emitted a shared emitter event. Add upstream-backed delayed-close tests and serialize confirmed closure or isolate socket/API generations before real integration.

**Actual inbound envelope and origin.** `models/Message.ts:18-28` declares provider msgId and cliMsgId strings. `UserMessage:90-99` computes self-origin from the **raw sender sentinel "0"**, not sender equality with account UID; it derives direct threadId from recipient for self messages, then mutates uidFrom/idTo sentinel fields to account UID. `GroupMessage:113-121` uses group idTo as threadId and the same self sentinel. `models/Enum.ts:1-4` establishes User=0 and Group=1. The older listener research harness replaces models with a simplified uidFrom===uid check; that harness cannot prove real self-envelope compatibility. Current normalizer's string-ID requirement is source-supported; it discards cliMsgId, timestamp and other potentially necessary reconciliation fields.

**Client-ID echo correlation.** `sendMessage.ts:350,366` generates clientId with Date.now internally; MessageContent has no caller clientId parameter, and returned SendMessageResult exposes only msgId. Attachment client IDs also originate internally (`sendMessage.ts:431-440`, `uploadAttachment.ts:170,216`). Incoming cliMsgId exists but the candidate drops it. Consequently no deterministic mapping from a durable outbox ID to the SDK's generated client ID is currently exposed. Correlate confirmed sends by canonical provider ID/account/thread, retaining unknowns; never infer safe retry from identical text or nearby timestamps. Reliable attribution of an echo arriving before the HTTP response, or after timeout, requires explicit pending-event reconciliation/design. A controlled SDK fork/wrapper exposing caller-stable IDs would require separate API/source validation, not an assumption of provider idempotency.

**Buffer media is feasible with host checks.** `models/Attachment.ts:1-11` provides the exact Buffer contract. `uploadAttachment.ts:177-187` checks Buffer instance, filename and extension; image size/dimensions come directly from supplied metadata (`205-217`), generic file size directly from metadata (`248-264`), and **chunk count is computed from that metadata**, while chunks are sliced from actual Buffer (`275-284`). Host must enforce integer totalSize===data.length, application max bytes/count, safe extension aligned to verified MIME/signature, and derived bounded positive image dimensions. These are not supplied by upstream's extension/provider-limit checks. Buffer JPEG/PNG uploads avoid filesystem path reads and imageMetadataGetter entirely; file-path metadata helpers require the getter (`utils.ts:336-379`). Do not add unrestricted paths or URLs. Existing app PDF/plain-text/JPEG/PNG limits can remain stricter than upstream; video/GIF support does not follow from this contract review.

**Upload completion and per-part feasibility.** Generic-file/video uploads install a WebSocket upload callback keyed by fileId and await it (`uploadAttachment.ts:314-332`); listener resolves it on control event (`listen.ts:298-306`). All chunks/attachments are requested concurrently and awaited with Promise.all (`uploadAttachment.ts:292-362`). There is no local completion timeout in this path; callback cleanup/timeout behavior additionally depends on context's callback map and transport continuity. The SDK's assembled API exposes one listener and factory-bound sendMessage/uploadAttachment (`apis.ts:321-323,446,476`). Calling `sendMessage({msg:"",attachments:[oneVerifiedBuffer]},threadId,type)` separately per attachment, plus a separate text call, is feasible from inspected control flow and yields per-call attachment IDs. It avoids aggregate text-before-media ambiguity, but changes caption/group behavior and may upload again after retries; uncertain calls must stay unknown. There is no public finalize-already-uploaded method in the audited sendMessage signature, so upload-first cannot be assumed to give resumable exactly-once media delivery. Each attachment call still contains upload/finalize uncertainty, requiring durable execution markers before calling it.

**Session refresh and assembly.** API exposes getOwnId (ctx.uid) and getCookie (CookieJar), from `apis/getOwnId.ts:3-5` and `apis/getCookie.ts:3-9`. `utils.ts:301-318` updates the jar from set-cookie. Persisting only original login cookies can miss refresh; any export interface must serialize the current jar through approved code, preserve external imei/userAgent, and encrypt atomically. Do not expose API/getContext/cookies to ordinary application users. API factory invalid-context errors stringify the entire context (`utils.ts:695-699`), so logging:false alone does **not** guarantee safe errors: sanitize at the facade boundary before logging/returning errors.

**Build/import limits.** `scripts/buildAPI.js` reads the local API directory and overwrites src/apis.ts; it does not itself access network or execute imported API modules. Source entrypoint exports models/Zalo plus enums and type-only API exports; Zalo imports API assembly, whose runtime imports cover the broad API set. Reviewed assembly creates Listener and binds factories; this does not establish every imported module's side-effect safety. Complete selected-artifact import graph, built package, lock/transitive install-script and advisory review remain required. No dependency version has been selected for production.
